# 渠道收款与支付 UE 方案

状态：**实施中。** 收款配置在渠道台；支付方式为可插拔 `Adapter` 插件。  
对照：Sub2API `/admin/settings` 支付设置、`docs/PAYMENT_CN.md`；线上 `https://www.tokpath.com/admin/settings`（已登录核对）；本仓库 `DESIGN.md`、`docs/01` §7.4、`docs/15` 渠道模型、`docs/05` 支付实体、渠道台 `/channel/*`。

本文回答三件事：

1. 支付配置放在哪一层（平台还是渠道）？
2. Sub2API 的哪一段 UI 原样借鉴，哪一段必须改掉？
3. 渠道管理员、平台管理员、终端用户各看到什么？

---

## 1. 结论（先看这里）

**平台只提供支付能力（支付宝官方 / 微信官方 / Stripe / 人工入账 / 兑换码）。每个渠道自己填商户号、自己开关、自己收钱。**

这和 Sub2API 不同。Sub2API 是单租户：全站一份支付设置，钱进同一个商户。TokenHub 是 A/B/C 多租户：官方站、批发商、OEM 各自有商户，用户按归属渠道付款，不能共用一套密钥。

| 放哪里 | 做什么 | 不做什么 |
| --- | --- | --- |
| 渠道台 `/channel/payments` | 开通通道、填凭证、限额、收银台文案、本渠道订单 | 不能改平台汇率 BPS、不能看其他渠道密钥 |
| 平台 `/admin/channels/{id}` | 看该渠道收款是否就绪、紧急停用、抽查订单 | 不替渠道填支付宝/微信/Stripe 密钥（除非官方渠道 A 的值班也是该渠道管理员） |
| 平台 `/admin/payments` | 跨渠道订单检索、退款审计、适配器总开关 | 不是「全站支付设置」 |
| 平台 `/admin/settings` | 2FA、熔断、演练、OEM 证书 | **不要**再放支付 |

第一版内置三个**官方**适配器：支付宝、微信、Stripe（另有人工入账，不出现在收银台按钮）。EasyPay / Airwallex 不做。代理商和个人推广员 **没有**收款配置（商户在渠道组织上，不在推广角色上）。每个渠道组织自己收钱：A 下的 B 与 C 下的 B 一样，用户按归属渠道付到该 B 的商户。通道不是写死在 Service/HTTP 里的：后续本地支付或聚合网关实现 `Adapter` 并 `Register` 后，渠道台通道卡和用户按钮会自动出现。

## 2. 为什么必须跟渠道走

用一个小例子：

- 用户甲在 TokenHub 官网注册，归属官方渠道 A。充值扫的是 **A 的支付宝商户码**，钱进平台。
- 用户乙也在 TokenHub 官网注册，但是通过批发商 B 的推广码进来。充值扫的是 **B 的支付宝商户码**，钱进 B。同一域名、同一套前端，商户不同。
- 用户丙打开 OEM 域名。充值扫的是 **C 的商户码**，回调写在 C 的域名上。

如果把支付设置做成 Sub2API 那样的全局「系统设置」：

- OEM 无法用自己的营业执照收款；
- B 的用户会把钱打进平台账户，和「B/C 先向平台预充值、终端用户向渠道充值」的账务模型冲突；
- 密钥、限额、客服码、商品名前缀都无法按租户隔离。

已有文档其实已经指向这条路，只是还没落到界面：

- `docs/01`：A 用户直接充值；B/C 终端用户也必须充值，按该渠道销售规则拿额度。
- `docs/05`：`topup_order` 带 `channel_org_id`；`billing_quota_issue_rules` 按渠道配置充值→额度 BPS，渠道不能改别人的。
- 渠道台已经有 `/channel/brand`、`/channel/plans`：品牌和套餐都是渠道资产。收款是同一类资产。

已实现：`payment_orders.channel_org_id` / `credit_minor`，以及 `payment_provider_instances`、`payment_channel_settings`、`payment_adapter_flags`。适配器走 `backend/internal/payment` 的 `Adapter` + `Registry`。

## 3. 平台 vs 渠道：功能目录

可以把它想成模型白名单的同一句话：**平台上架能力，渠道决定用不用、怎么用。**

### 3.1 平台提供（功能）

- 适配器：支付宝官方、微信官方、Stripe、人工入账、兑换码；注册表可再挂本地支付 / 聚合网关。
- 下单 / 查单 / 退款 / webhook 验签 / 超时补单的公共实现。
- 全局紧急开关：某个适配器故障时，平台可停用「微信」，所有渠道的微信按钮一起消失；渠道自己的凭证还在。
- 充值→额度换算 BPS：按渠道一行，平台财务写，渠道只读并看到预览。
- 跨渠道订单检索与审计（财务角色）。

### 3.2 渠道配置（商户）

- 开哪些按钮：支付宝 / 微信 / Stripe（第一版没有「官方 vs 易支付」二选一，因为不上 EasyPay）。
- 每个按钮后面的商户实例：AppID、密钥、单笔/每日限额、是否允许退款。
- 收银台：快捷金额、超时、待支付单上限、商品名前缀/后缀、帮助图和帮助文案。
- 本渠道订单：补单、退款（若该实例开启退款）、失败原因。

### 3.3 明确不做

- 渠道 BYOK 上游模型 Key（已否决）。收款商户 **不是** 上游 Key，渠道可以且必须自带。
- 代理商/个人推广员各自一套支付宝。收款主体是 `channel_org`。C 下 B 使用 C 的商户。
- 平台代收后再分账给渠道（第一版资金直达渠道商户；渠道向平台的批发预充值走现有人工/授信，不和终端用户收银台混在一起）。
- 把支付塞进 `/admin/settings` 或用户 `/app/settings`。

## 4. 对照 Sub2API：搬什么、改什么

Sub2API 的支付设置在「系统设置 → 支付」一个超长 Tab 里，和 SMTP、Codex 指纹、OAuth 共用一个「保存」。那是单租户后台。我们只借它的**通道卡片 + 凭证弹窗 + 用户收银台节奏**，不借它的信息架构。

### 4.1 原样借鉴（交互骨架）

- 用户侧三个品牌按钮：支付宝蓝、微信绿、Stripe 紫，带官方图标。
- 快捷金额筹码 + 自定义输入。
- 付款前先看到「应付 / 手续费 / 钱包到账」。
- 选完金额再出码：`select → paying（二维码/JSAPI/Payment Element）→ 成功`，支付中不要把用户踢去空白新路由。
- 服务商实例：名称、启停、退款开关、每实例限额、拖拽排序（仅同一通道有多实例时出现）。
- 凭证弹窗按类型出字段；已配置密钥留空表示不覆盖。
- 回调 URL 自动生成，管理员只复制，不手拼。
- 支付宝：桌面当面付优先，失败回退电脑网站支付；移动可 WAP 或当面付唤起。
- 微信：桌面 Native；微信内 JSAPI；其它手机浏览器 H5。
- Stripe：页内 Payment Element。
- 超时先查上游再标过期。

### 4.2 必须改掉的 UE（Sub2API 的问题）

| Sub2API | 问题 | TokenHub |
| --- | --- | --- |
| 九个系统设置 Tab + 底下一颗总保存 | 改支付会误伤 SMTP；支付不像「设置」 | 收款是渠道台一级入口，规则页单独保存 |
| 三层开关：启用支付 × 启用服务商类型 × 实例开关 × 前台来源 | 配完仍可能前台空白 | 每个通道一张卡：关 / 配置中 / 沙箱 / 已开通 |
| 支付宝还要选「官方 or 易支付」 | 第一版没有易支付，这是泄漏的实现细节 | 通道卡直接对应官方适配器 |
| Stripe 卡片上把 card/alipay/wxpay/link 做成可点徽章 | 和「支付宝通道」撞名 | Stripe 卡只展示「卡 / Link」能力，不当成第四、第五个收款按钮 |
| 实例行上三个 Toggle 随时点 | 误关退款、误开生产 | 启停要确认；退款策略放进「⋯」菜单 |
| 限额、取消频率、商品名前缀和凭证挤在一页 | 渠道管理员第一次开通会被吓跑 | 先开通三通道；限额/文案放「收款规则」，高级项默认折叠 |
| 1 CNY → N USD 只在倍率≠1 时显示 | 我们账本是 USD minor，支付宝收 CNY | **永远**展示「支付币种 → 钱包入账」，并套用该渠道只读 BPS |
| 硬编码快捷金额 10…5000 | 渠道客单价不同 | 渠道在规则里自定义筹码 |
| 主按钮文案「创建订单」 | 像后台 | 「支付 ¥100，到账 $14.00」 |
| 套餐页不说明谁能自动续费 | 我们规定只有 Stripe 能代扣 | 选支付宝/微信时横幅：到期需手动续费 |

视觉跟 `DESIGN.md`：纸/碳表面、`rounded-card`、`th-eyebrow`、金额用 `ledger-row`。支付宝/微信/Stripe **商标色保留**（这是支付品牌识别，不是搬 Sub2API 的灰底后台）。

### 4.3 线上核对（tokpath.com）

已登录查看 `https://www.tokpath.com/admin/settings`。它就是 Sub2API 那套九 Tab 系统设置，支付是其中一页，不是渠道资产。和源码一致、实现时不要再抄的位置：

- 支付和 SMTP、OAuth、网关指纹挤在同一保存流里。
- 「启用的服务商」同时列出易支付、支付宝、微信、Stripe、Airwallex；线上已有一条支付宝官方实例。
- 添加服务商弹窗把回调拆成只读前缀 `https://www.tokpath.com` + 路径 `/api/v1/payment/webhook/alipay`。这个拆法要保留，但前缀必须改成**该渠道的 API/OEM 域名**，不能写死官网。
- 订单、支付看板、订阅是侧栏独立页，不在设置里。渠道台应对齐：通道/规则在收款下，订单仍是列表而不是设置字段。

## 5. 渠道台信息架构

在现有渠道侧栏「渠道」分组、品牌旁边增加 **收款**：

```text
/channel                    总览
/channel/users              用户
/channel/models             模型
/channel/plans              套餐
/channel/payments           收款     ← 新增，默认落在「通道」
/channel/promos             推广
/channel/brand              品牌
```

`/channel/payments` 用和用户设置一样的 `SettingsSubnav` 子导航，不要再做九个系统 Tab：

| 子页 | 给谁用 | 内容 |
| --- | --- | --- |
| 通道 | 渠道管理员 | 注册表里 `UserFacing` 的能力卡 + 开通向导（字段由插件 schema 渲染） |
| 规则 | 渠道管理员 | 快捷金额、超时、待支付上限、商品名、帮助图文；折叠：取消频率、手续费 |
| 订单 | 渠道财务/管理员 | 本渠道支付单，状态筛选，行点开抽屉 |
| 人工入账 | 渠道财务 | 兑换码、认领转账（平台提供的能力，配置仍在本渠道） |

### 5.1 通道页：三张能力卡（主画面）

不要一上来列出「服务商实例表格」。先问：这个渠道的用户能不能用支付宝？

每张卡四个状态，文案写进人能看懂的字：

| 状态 | 用户充值页 | 卡片上看到 |
| --- | --- | --- |
| 未开通 | 不出现该按钮 | 主按钮「开通支付宝」 |
| 配置中 | 不出现 | 缺哪些字段（「还差公钥」） |
| 沙箱可用 | 仅测试账号或明确沙箱环境 | 徽章 `SANDBOX`，可「测一笔」 |
| 已开通 | 出现按钮 | 绿点 + 最近一笔成功时间 |

点「开通」进入分步弹窗（借鉴 Sub2API 凭证表单，改成向导）：

1. **商户身份**：名称（仅内部）、沙箱/生产。
2. **凭证**：字段与 Sub2API 官方通道一致（支付宝 AppID/私钥/公钥；微信商户号与 APIv3；Stripe sk/pk/whsec）。
3. **回调**：只读 URL + 一键复制。C 渠道用 OEM 域名；A/B 用平台 API 域名。说明「系统用商户号识别是哪个渠道，不必把渠道 ID 写进 URL」。
4. **限额（可选）**：单笔最低/最高、每日上限；留空用渠道规则默认值。
5. **测连通**：类似邮件设置的「测试连接」。失败不让点「上线」。

「上线」使用现有 `ConfirmButton`（改凭据是高风险操作）。同一通道可以有多个实例（备用商户、限额分流）；**第二张实例出现后**才显示负载均衡（轮询 / 当日最少金额）和拖拽。只有一个商户时不要露出「负载均衡」四个字。

### 5.2 规则页

默认只露出：

- 快捷金额筹码（可增删，3–8 个）
- 最低/最高单笔
- 订单超时分钟
- 帮助文案 / 客服图（OEM 充值页用自己的码）

折叠「高级」：

- 商品名前缀/后缀（防风控，给懂的人）
- 最大待支付单数
- 取消频率
- 充值手续费（渠道自己加价手续费；BPS 换算仍只读）

页顶只读账本预览（这是相对 Sub2API 最大的诚实性优化）：

```text
用户付  ¥100.00
手续费  ¥  1.60   （若渠道设了 1.6%）
到账额度 $ 14.00   （本渠道换算 1 USD = 7.15 CNY，BPS 由平台设定）
```

渠道改不了 BPS。点「为什么是这个比例」展开一句：批发授信和额度发放是平台政策，避免渠道把 1 块钱充成 100 块额度。

### 5.3 订单页

替换现在平台支付页「手填 pay_… 再确认」的形态。

- 状态筹码：待支付 / 已付待入账 / 已完成 / 失败 / 退款中
- 表：时间、用户、通道、应付、到账、状态（`ledger-row`，金额右对齐等宽）
- 行 → 抽屉：时间线（创建、回调、入账、补单），失败原因原文（脱敏），操作：补单、退款（确认）、关闭
- 没有权限或实例关闭退款时，退款按钮不出现，而不是点了报错

### 5.4 A / B / C 同一套页面，文案不同

| 渠道 | 通道页提示 |
| --- | --- |
| A 官方 | 资金进入本渠道（平台）商户。用户在官网充值。 |
| B 批发 | 资金进入本渠道商户。用户仍在 TokenHub 域名付款，系统按用户归属选你的通道，不会让用户自己挑渠道。 |
| C OEM | 资金进入本渠道商户。回调和收银台走你的品牌域名。 |

B 渠道品牌页只读「使用平台品牌」；收款页 **可写**。品牌跟收款解耦：B 不换皮，但必须能用自己的支付宝。

## 6. 平台管理台怎么配合

平台 **不** 出现「系统设置 → 支付设置」。

| 页面 | 角色 | UE |
| --- | --- | --- |
| `/admin/channels/{id}` | 运营 | 「收款就绪」灯：每个已注册且面向用户的插件一张，未开通 / 沙箱 / 已开通。不展示密钥。可「紧急停用该渠道在线支付」（确认）。 |
| `/admin/payments` | 财务 | 跨渠道订单表，多一列渠道。筛选渠道/适配器/状态。可退款（确认+审计）。不再当配置页。 |
| `/admin/settings` | 技术值班 | 保留支付**演练**（伪造签名必须拒绝），这是运维，不是商户配置。 |
| 适配器目录（可放渠道详情或独立只读） | 超管 | 平台级「停用微信适配器」。文案：所有渠道的微信按钮将隐藏，已填凭证保留。 |

官方渠道 A 的密钥：由 **A 的渠道管理员**在 `/channel/payments` 填写。平台超管若也是 A 的 `channel_admin`，走渠道台，不在系统设置里复制一份表单。

## 7. 终端用户收银台（按渠道解析配置）

入口仍在用户钱包/套餐，公共站充值页按 **登录用户的 `channel_org_id`** 拉配置，不按「当前站点有没有全局支付」。

```text
登录用户
  → channel_org_id
  → 该渠道已开通的通道
  → 展示按钮、限额、帮助图
```

OEM 域名再校验 `brand_id` 与渠道一致，防止串站。

**空状态**（渠道一个通道都没开通）：

- 标题：当前渠道尚未开通在线支付
- 说明：可使用兑换码，或联系渠道客服（展示该渠道规则里的帮助文案/图）
- 不要写「支付功能未启用」这种内部话

**有通道时的版式**（相对 Sub2API 四张叠卡）：

- 左：金额筹码 + 通道按钮
- 右：账本摘要（应付、手续费、到账额度、币种），滚动时吸顶
- 主按钮：`支付 ¥100，到账 $14.00`
- 购买套餐：选支付宝/微信则横幅「不支持自动扣款，到期需手动续费」；选 Stripe 则「到期按同一支付方式续费，可随时取消」

微信内打开：不先出大二维码，直接走 JSAPI。支付宝 App 环境：按渠道开关尝试唤起。

支付中：倒计时、订单号等宽、「我已付款」触发查单、取消订单。成功后用账本行展示到账，而不是只写 OK。

## 8. 数据与权限（实现时必须对齐）

现有 `payment_orders` 缺渠道维度，补这些边界：

- `payment_orders.channel_org_id` 必填，下单时从用户归属写入，不信任客户端。
- `payment_provider_instances.channel_org_id`：凭证按渠道隔离，加密存储，列表不回显密钥。
- `payment_channel_settings`：快捷金额、超时、帮助图等，一行一个渠道。
- Webhook 用适配器路径 + 载荷里的商户号定位实例（`app_id` / `mch_id` / Stripe account），避免把内部渠道 ID 暴露给支付宝后台。
- 渠道 API 只返回本 `channel_org_id`；平台财务列表可按渠道筛。
- 改凭证、上线、退款：`ConfirmButton` + 确认头 + 审计。启用生产通道视为改凭据级高风险。

兑换码/人工入账也挂在渠道：码不能跨渠道核销。

## 11. 如何加一个本地支付插件

后端对照 Sub2API 的「一个 Provider 一个文件 + 注册表」，但接口是本仓库自己的 `Adapter`：

1. 新增 `backend/internal/payment/driver_xxx.go`，实现 `Adapter`（可先 embed `sandboxDriver` 跑通 HMAC webhook）。
2. 在 `Spec()` 里声明 `ID`、`Kind`（`local` / `gateway` / `official`）、`PayCurrency`、`CheckoutMode`、`UserFacing`、`Credentials` 字段。
3. 在 `newBuiltinRegistry()` 加一行 `MustRegister(...)`。
4. 渠道台通道卡、用户收银台按钮、平台就绪灯、`GET /admin/payment-adapters` 都从注册表渲染，**不要**在 HTTP 或前端写死支付宝/微信/Stripe。
5. 换成真实 SDK 时，只改该文件的 `CreateCheckout` / `ParseWebhook` / `QueryOrder` / `Refund`。Service 继续负责订单、幂等、入账。

人工入账把 `UserFacing: false`，不会出现在收银台。
