## 支付手续费、付款币种与实际收款分离（2026-11-12）

- 经营方配置的手续费是向付款人收取的费用，可按预计成本设置，也可为零；支付商自己的收费独立发生，不承诺两者相等或保证经营方净到账。沿用现有设置表单，只补充说明，七种语言同步。
- 充值、购包和采购输入阶段移除实时手续费及总额预览；提交后的支付商页面展示最终付款金额。线下付款沿用提交后的办理说明。余额与佣金提现继续显示申请总额、费用和净额。
- 支付商支持传入订单币种时直接传入本金加经营方手续费；只有通道不支持时才使用汇率报价。Stripe 按支持的订单币种下单。KVoucher 的一般订单接口虽接受 USD，本次沙盒 Gkash 收款接口实际返回 INVALID_CURRENCY，因此该路径继续先报价成 MYR；不把通道另外收取的费用误判为本单金额冲突。
- 客户权益、订单付款关联金额与经营方真实到账分开保存。例：充值本金 100 USD、经营方收费 2%，向通道提交 102 USD；通道向客户收取 103 USD，最终给经营方 100.02 USD 时，客户余额增加 100 USD，经营方实际收款记录为 100.02 USD。跨币到账保留真实币种与金额，未知净到账保留未知，报表不把支付商付款总额或订单折算额当作经营方到账，也不重复减去已包含在净额中的费用。
- 按用户明确例外，KVoucher 收到券码后按实际券面额和币种记录资产入账；后续兑换不纳入系统。核对订单与收到券的面额、数量，提券结果及入账保持幂等，不将 Gkash 对付款人加收的金额作为券资产。
- 未付款可在原订单选择另一方式。更换前核实原通道明确尚未付款，处理中或结果不明时继续核实；保留旧付款及其费用快照，返回原方式复用原付款，旧付款稍后成功仍按原快照处理，不重复交付。采购复用原付款表单和方式选择，不增加页面。
- 本节替代 2026-11-11 条目中“通道付款表单金额必须等于系统提交金额”的旧判断；仍校验真实订单关联、有效金额和币种、足额付款及券面额，不将创建付款链接当作收款成功。

验证：425 项前端测试、生产构建、类型检查、25 项 OpenAPI 契约与生成检查通过。交易、支付、账本、报表、合作、异常退款整包数据库回归及相关 portal HTTP/数据库回归覆盖原币净到账、未知到账、费用分离、重复回调、未付款切换、处理中禁止切换和旧付款延迟交付。所有后端包编译通过。数据库测试串行使用隔离库；未配置的 S3 外部验收不计入通过项。

页面验收使用隔离 PostgreSQL、真实 API、生产前端和合成支付通道：核对客户充值不预览加费合计、提交后进入付款页、未付款核实返回正常提示，以及平台、OEM、渠道的精简支付设置和七语言文案。截图在本机 `../local/payment-semantics-20261112/payment-fee-settings-zh.png`。

外部验证边界：KVoucher 沙盒确认了 MYR 下单、通道自加费用及 USD 无法进入 Gkash 的行为；未进行真实商户付款或后续兑换，沙盒提券未执行。收券、交付与账本闭环使用本地合成 PIN 和数据库集成测试验证，不能替代实际商户验收。没有手工读取或解密测试站的商户凭据。

## 充值付款指引失败的处理（2026-11-11）

- 充值和套餐订单已保存、随后支付通道创建指引失败时，返回原订单及可读说明，避免界面把它当作订单未创建。充值提交结果直接显示付款暂停原因；原单详情保留本金、手续费和未付款状态。已明确失败的订单仍按原有规则允许取消，结果未知的订单不能盲目取消或换通道。
- KVoucher 返回的币种或金额与本单报价不符时，使用专门的付款核对错误，不再误报“版本冲突”。继续拒绝提供未经核实的付款表单，不放宽金额校验，不记收款、不增加客户余额；相同提交编号的重试返回同一张订单，不再创建外部订单。
- 仅记录本地订单编号、预期及通道返回的规范化币种和金额，未知币种不原样输出；不记录密钥、签名表单、响应正文或客户资料。旧失败记录没有具体原因时只说明付款指引不可用，不推断为金额不符。按用户要求不另行处理旧测试订单。
- 客户页面在付款指引不可用时隐藏继续付款区域，保留原有查询；充值订单的记录链接回到充值页。新增文案同步七种语言及后端生成目录。

验证：KVoucher 币种/金额不符、缺少金额及诊断脱敏测试，充值与套餐创建的真实 HTTP/PostgreSQL 回归、原单重试、无收款事实/无余额入账、报价失败取消权限及统一手续费回归通过。421 项前端测试、后续相关组件与语言检查、类型检查、生产构建、25 项 OpenAPI 契约及生成检查通过。使用隔离数据库、真实 API、生产前端和合成 KVoucher 返回值完成点击创建充值订单、结果提示、刷新原单及七语言页面验收，证据在 `../local/kvoucher-live-20261111/checkout-paused-zh.png`。

验证边界：以上确认了错误分类和失败后的展示问题。正式 KVoucher 通道本次返回金额没有保存在旧诊断日志中，仍未取得实际差异，不能据此宣称正式商户充值已恢复；未手工读取/解密商户凭据，也未向真实通道提交付款。

## 精简后台任务异常（2026-11-11）

- “任务恢复”改为“后台任务异常”，只展示自动重试耗尽后仍未恢复的事项，按最近失败时间倒序排列。移除正常任务列表、状态筛选、原始记录详情和恢复备注输入；保留一次恢复确认。
- 同一事项的定时检查按既有调度标识汇总，后续成功后自动移除旧失败；正在自动重试时显示进度说明，不允许恢复历史轮次。一次性任务各自保留，不按任务类型误合并。超时耗尽也记录失败时间，恢复期间保持异常可见；恢复不修改原业务编号或重置尝试历史。
- 影响对象显示经营方名称、品牌域名或公开模型，页面不返回原始任务负载、业务键和外部错误正文。平台技术权限保持不变，OEM 和渠道不能读取或恢复任务。

验证通过：任务队列整包数据库回归，以及后台任务异常与调度的 HTTP/数据库专项，覆盖失败合并、成功移除、恢复幂等、过时轮次拒绝、分页、错误脱敏和 OEM/渠道权限隔离；全部 Go 包编译、419 项前端测试、生产构建、类型检查、25 项契约测试与语言同步检查通过。最初并行构建期间一项语言完整性测试超时，限制前端测试并发后整组复跑通过。

## 统一支付方式手续费与异常退款退费（2026-11-08）

- 设置集中到“支付方式与手续费”，每种方式仅配置不收费、固定金额或费率之一，适用于该方式支持的充值、直接购包、下级采购、余额提现与佣金提现。收款连接在同页维护；删除两类提现页面的重复方式设置。
- 收款在外部本金之外加收，充值和 ATG 交付只按本金；提现从申请总额内扣费。内部余额、佣金抵扣不收支付手续费，混合付款只对外部本金计费。以清算币种最小支付单位四舍五入，不引入全局财务换汇。
- 确认前展示本金、费用和合计，确认后保存不可修改的规则版本及金额快照。旧页面遇调价必须重新核对；网络结果不明时重试同一订单和快照。自动补货授权保存费用与含费付款上限；线下先收款后登记采购也明确区分本金与手续费。
- 普通收款页不再要求操作员登记商户手续费，不再把未知成本列成正常办理待办。可靠通道费用可自动保存，未知仍为未知；客户支付手续费与商户实际成本分别记账、报表及导出。

## 交付内容

**经营体系。** 平台、OEM 和渠道分别经营，品牌、客户服务归属、供货关系与推广关系分开建模。注册邀请、两跳推广、员工权限、独立复核、开业检查、分项经营状态、风险冻结和退出均有流程。平台可配置 OEM 域名、配色及 Logo；直属上级可配置渠道配色及 Logo，逐字段继承品牌默认外观。合作关系不自动开放下级客户财务。

**资产和销售。** 新账本使用 NUMERIC(38,18)，记录来源、占用、分录、余数与追加冲正。通用套餐、版本化报价、购赠比例、先到期先用、订单资金组合、交付、续费授权、促销、KOL 让利、佣金、提现、采购和补货已接通。采购价格与调用价格分开；采购成本移动加权平均；超卖仅扩大可售承诺，采购不足仍停止调用。到期购买价值推动确认支出资格，不产生调用佣金。

**模型服务。** 平台统一维护公开模型、供应商密钥、能力、路由和分层授权，经营方独立定价。受理时固定零售及各层批发快照，原子占用客户和采购责任，按可靠用量结算。多个 Key 共享账户额度，自然周期预算不划拨资产。同步、流式、异步和网页体验共用计费；失败尝试、用量未知、超额、幂等回读、路由健康与恢复均有实际处理路径。Key 创建、预算查询和受理统一使用数据库业务时钟。

**资金处理。** Stripe、支付宝、微信、NOWPayments、自有钱包只读 EVM 核验及线下登记均有具体实现；材料不足时保持待配置。收款、估值、订单分配与交付分离。原币到账但无法核实实际付款时点估值时，保留原币责任并进入财务待办，不凭下单汇率制造 USD。退款责任、原执行指令、部分实付、新目的地授权、通道费用及迟到事实分别追踪，防止重复清债。系统不发起银行或链上提现转账。

**责任和接管。** 普通套餐不自由退款；错误扣费、支付余额退回、异常履约退款、外部扣回及错误佣金按原来源处理。渠道接管清理在途责任、复核快照、一次作价抵扣采购、原子承接客户权益与推广链，双方差额独立结清。原 Key 继续服务，接管后收益与风险归品牌。关闭客户或经营方时，所有历史订单的待估值原币及已收未分配款仍是未结责任，不能借关闭订单绕过。

**门户和运营。** 客户工作台、经营后台、合作管理、平台技术管理、通知、报表、开票申请及私有文件、对账和导出已接入。经营表单使用有权限的引用选择器和版本管理。OpenAPI 198 条路径、177 份 Schema，111 份经营写入元数据都有明确 DTO 和自动漂移检查。前端金额以十进制字符串处理，显示近似值不改变提交与结算精度。

**运行基础。** 新库代际为 `tokenhub-operator-v2`，迁移命令独立执行并检查校验和。API/worker 就绪检查不自动迁移。持久任务租约、fencing、重试、失败待办、事务 outbox/inbox、Redis 限流、私有结果加密及到期删除、指标访问限制、备份和隔离恢复已实现。普通 API 内容不长期保存；同步回读默认 5 分钟，异步结果默认 24 小时。

检查包含 PostgreSQL 权限与状态回归、真实私有 MinIO Logo 上传、前端 379 项测试、生产构建、25 项 OpenAPI 契约检查，以及平台/OEM/渠道浏览器操作。四语言外观面板逐一检查。隔离浏览器中的域名验证使用合成提供方，仅用于验证交互与授权，不代表真实 OEM 公网 DNS 或证书已经开通。真实接入仍由平台完成统一网关配置、OEM 配置 DNS 后核实。
