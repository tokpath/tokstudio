# TokenHub 逐项讨论清单

这份清单用于一轮只确认一个主题。每个主题都有建议默认值；确认后再把答案回填到 PRD，并进入下一项。

## 已确认决策

### D1. 计费单位、币种与价格层级：已确认

- 内部统一使用 USD 定点数记账，展示层可换算 CNY/JPY。
- 价格拆分为 `upstream_cost`、`channel_wholesale_price`、`customer_sell_price`。
- 历史请求保存价格版本和价格快照；价格调整不改写历史账单。

### D2. 余额扣款时点：已确认

- 请求前执行预授权；余额不足以覆盖预授权金额时，请求不发送到上游。
- 收到上游最终 usage 后按实际金额结算，并释放多余预授权。
- 流式请求被客户端中断时，按上游已产生的实际 usage 结算。
- 上游成功但没有 usage 时，不按估算值扣款，进入 `usage_pending_reconciliation` 待对账状态。

### D3. 首批提供商、协议和账号类型：已确认（媒体范围补充）

- P0 支持 OpenAI Chat Completions、Responses 和 Anthropic Messages。
- 首批通用提供商为 OpenAI、Anthropic、Google Gemini；兼容 OpenAI 协议的提供商支持自定义接入。
- P0 增加统一视频/多媒体异步任务能力，首个重点媒体模型为 Seedance 类模型。
- P0 媒体任务至少支持提交、查询、回调、下载、幂等、取消、预授权和媒体单位计费。
- OAuth 订阅账号暂列 P1；P0 先支持 API Key 或提供商签发的服务凭据。

### D3.1 Seedance 首发接入渠道：已确认

- P0 同时接入火山方舟直连和 OpenRouter。
- 两者作为独立上游路由候选，可按优先级、价格和健康状态切换。
- 每次请求记录最终真实提供商、上游任务 ID、usage 和账单来源。
- 禁止聚合提供商回流 TokenHub 自身，防止循环代理和重复计费。

### D3.2 P0 媒体能力边界：已确认

- P0 支持视频生成：文生、图生、首帧、首尾帧、参考图/参考视频/参考音频。
- P0 支持时长、分辨率、宽高比、帧率和原生音频开关等媒体参数。
- P0 支持视频编辑/延长，前提是上游模型声明对应能力。
- P0 包含图像生成/编辑，作为视频参考素材和基础媒体能力。
- 独立音频生成、语音转写、视频理解、复杂视频时间线编辑放到 P1。

### D3.3 模型目录与价格同步：已确认

- 提供商自动同步模型、能力、参数、媒体规格和价格，结果先进入 `draft`。
- 管理员审核公开模型 ID、上游映射、路由和销售价格后才发布到客户白名单。
- 价格变更生成新版本，不改写历史账单；下线模型标记 `deprecated` 并保留历史记录。
- 支持管理员手工创建和覆盖模型、映射和价格。

### D4. 路由与 fallback：已确认

- 每个公开模型独立配置路由组；Seedance 默认火山方舟直连优先，OpenRouter 备用。
- 默认只在同一模型的不同提供商间 fallback；跨模型 fallback 必须显式配置。
- 可重试连接超时、408、429、5xx 和明确的临时不可用；不重试参数错误、认证失败、内容安全拒绝和模型不存在。
- 流式响应开始返回正文后不切换提供商。
- 异步视频任务在上游已返回任务 ID 后不自动重复提交；未知状态进入待确认/对账。
- 每次切换记录原始提供商、失败原因、最终提供商和账单来源。

### D5. 预算、额度与限流：已确认

- P0 只保留用户余额、API Key 的禁用/过期/RPM/并发限制，以及 B/C 渠道累计消耗额度。
- 余额不足返回 `402`；API Key 或渠道停用返回 `403`；RPM/并发/提供商限流返回 `429`；无可用提供商返回 `503`。
- P0 不引入 workspace/project 多层预算、复杂继承、TPM 和企业级 lifetime 预算；这些能力后续按真实客户需求扩展。

### D6. 用户渠道归属：已确认

- 每个终端用户必须归属于一个 `channel_org_id`。
- 官方渠道 A 是平台自营的特殊渠道；B/C 是批发商或 OEM 渠道。
- 用户通过代理商/KOL 注册时，额外记录 `acquisition_role_id`，用于具体推广归因和佣金。
- 用户归属和推广来源由服务端固化，用户不能自行切换渠道。

### D7. A/B/C 额度路径：已确认

- A 官方渠道：终端用户直接充值，API 消费从用户余额扣除。
- B/C 渠道：B/C 代理商先充值，平台确认到账后再由平台管理员授予/释放渠道可用额度。
- B/C 代理商在渠道可用额度内向下属终端用户分配子额度；引流来的用户在该代理商/渠道名下消费。
- B/C 名下终端用户也必须充值；系统按该代理商的销售价格/额度规则向用户发放服务额度。
- B/C 终端用户消费时扣减自己的服务额度，并将 usage 归属到该代理商和渠道；不对同一请求重复扣用户充值余额和渠道余额。
- 代理商充值、平台授予额度、用户充值、用户额度发放、回收、调整和消费均生成独立流水；发放额度不得超过渠道可用额度。

## 讨论顺序

### D1. 计费单位、币种与价格层级（已确认）

已确认：内部统一 USD 定点记账；模型价格拆为 upstream_cost、channel_wholesale_price、customer_sell_price；展示层再换算 CNY/JPY。

### D2. 余额扣款时点（已确认）

已确认：请求前预授权，收到最终 usage 后结算，多余预授权释放；usage 缺失进入待对账。

### D3. 提供商与模型范围（已确认，媒体范围补充）

已确认：P0 支持 OpenAI Chat/Responses、Anthropic Messages、Google Gemini 接入，并增加 Seedance 类视频/多媒体异步任务；OAuth 订阅账号放到 P1。

### D4. 路由与 fallback（已确认）

已确认：同模型优先在不同提供商间 fallback，跨模型必须显式配置；流式响应开始后不切换；视频任务拿到上游任务 ID 后不自动重复提交；未知状态进入待确认/对账。

### D5. 用量、预算与限流（已确认）

已确认：P0 采用用户余额 + API Key 限流 + B/C 渠道额度，暂不做企业网关式多层预算。

### D8. 分销佣金承担方

已确认佣金比例由平台统一设置，可按渠道、代理商等级、代理商角色和 KOL 层级配置，也可针对单个主体覆盖；B/C 不能自行突破或改写平台最终比例。佣金按 usage 事件冻结，并绑定到代理商/渠道的实际消费和已确认充值额度。A/B/C 全部由平台承担佣金，佣金不扣减 B/C 用户服务额度或渠道服务额度。

### D8.2 充值与额度换算：已确认

- 平台按渠道配置“充值金额 -> 服务额度”的换算规则，B/C 代理商不能自行修改。
- B/C 下属用户默认按 1:1 获得终端服务额度。
- 代理商实际充值、平台授予额度、用户充值、用户额度、终端消费、渠道批发成本和佣金基数分别记账。

### D9. 归因与代理层级

已确认：唯一归因；A/B/C 组织隔离；代理商 -> 1 级 KOL -> 2 级 KOL，停止无限多级。代理商可看自己名下用户运营和消费明细；1 级 KOL 可看自己用户及 2 级 KOL 汇总；2 级 KOL 只能看自己直接引流用户。敏感身份信息需脱敏，prompt/completion 原文不对分销角色开放。

### D10. 充值、退款与结算

已确认：只退未消费余额；已消费部分不退款；已产生佣金的消费同步冲正；渠道停用后冻结新消费，但保留余额、账务和历史数据。

### D11. 隐私、日志与合规

已确认：默认不保存 prompt/completion 原文；保存 request/attempt/usage 元数据；媒体输入和输出使用受控对象存储，结果通过签名 URL 提供，默认保留 7 天后自动删除。零数据保留和区域隔离作为后续企业能力。

### D12. OEM 与运营后台

已确认：OEM 需要独立用户充值站点域名、API Gateway 域名和管理后台域名，并支持 Logo、配色、站点名称等品牌配置。域名采用 CNAME 接入并自动签发 HTTPS 证书；平台仍统一维护底层提供商、模型和账务能力。OEM 可选择展示哪些平台模型，并可在平台底线和额度约束内创建自定义套餐及销售价。

### D13. 终端账号与 API Key

已确认：一个终端用户可以创建多把 API Key；每把 Key 支持名称、创建时间、最后使用时间、禁用、过期、模型白名单和 RPM/并发限制。完整 Key 支持长期查看；数据库保存加密密文和 hash 索引；查看、复制、轮换、禁用和过期均写审计日志。

### D14. 注册登录与渠道归因：已确认

已确认：P0 支持邮箱密码、邮箱验证码和 Google OAuth；GitHub OAuth 放到 P1。推广链接通过服务端暂存 attribution，注册完成后固化 channel_org_id、acquisition_role_id 和 brand_id；B/C/OEM 域名沿用同一身份系统。

### D15. 充值支付方式

已确认支付采用可插拔适配器架构。国内支付与国际支付同步进入 P0：首批在线适配器为 Stripe、支付宝和微信支付，同时支持人工入账/兑换码。平台核心统一处理充值订单、支付状态、验签、幂等、退款、对账和额度发放；适配器只负责各支付平台的下单、查询、退款、webhook 和支付方式能力差异。

自动续费按适配器能力处理：Stripe 支持完整的支付方式引用和自动续费；支付宝/微信支付若商户资质或产品能力不支持自动扣款，则订阅进入到期提醒和手动续费流程，不得伪造自动续费成功。

### D16. 模型访问权限

已确认模型权限首先按路由 Provider 下的上游模型管理：Provider 可发现很多模型，平台管理员选择启用哪些模型；渠道再选择允许展示/销售的模型；用户/API Key 可进一步限制。客户看到的 `openai/gpt-5.6` 表示 OpenAI 模型本身，平台可以在 OpenAI 直连、OpenRouter 等多个路由 Provider 间自动选择；客户目录同时展示模型厂商和 Provider 可用状态。客户可显式指定 Provider 顺序或仅允许某个 Provider，默认仍由平台自动路由。模型不可用、渠道未授权或 Key 不在白名单时，返回结构化 `model_not_allowed`。

### D17. Provider 对外展示

已确认：模型目录展示模型厂商、可用 Provider、状态、平台基础销售价和最近延迟/成功率；不展示 Provider 独立价格、平台上游密钥、内部成本价和敏感故障细节。Provider 状态使用 available、degraded、unavailable、maintenance 等简单状态。Provider 之间的成本差异属于平台内部盈利和运营数据；渠道自定义套餐可在平台底线内设置自己的销售价。

### D18. 充值模式与订阅套餐

已确认：P0 同时支持预付费按量计费、月度订阅、包月额度/Token、赠送额度和自动续费。订阅权益与现金钱包分开记账，支持到期、续期、退款、冲正和续费失败状态。

包月额度已在 D18.1 确认为按模型/能力配置的多计量权益，不采用单一 USD 额度池。

### D18.1 套餐额度单位：已确认

- 套餐按模型/能力配置多种额度单位。
- 支持 `token`、`video_second`、`image_count`、`request_count`、`usd_credit` 等权益类型。
- 订阅权益与现金余额分开记账，消费时按权益规则扣减。

### D19. 套餐创建与渠道销售

已确认：平台提供基础模型能力、计费单位、批发成本、能力上限和风控规则；A/B/C/OEM 渠道可以基于平台允许的模型和额度范围创建自定义套餐，设置套餐名称、组合、销售价和营销文案。平台也可以创建全局套餐，并对渠道套餐设置成本底线、额度上限和佣金约束。

### D20. 渠道自定义套餐发布流程：已确认

- 渠道创建套餐后，系统自动校验价格底线、额度上限、模型权限、能力边界和风险规则。
- 正常套餐校验通过后直接发布；低于价格底线、超出额度上限或包含高风险模型/能力的套餐进入平台人工审核。
- 平台可随时下架、冻结或强制修改渠道套餐；相关变更不改写已购买订单和历史账单。

### D21. 套餐权益优先级与过期规则：已确认

已确认采用以下默认规则：

- 消费顺序为“即将过期的赠送额度 -> 当期套餐额度 -> 用户充值余额”；同一优先级按最早到期（FIFO）扣减。
- 赠送额度默认有明确到期日，过期自动失效且不可提现；平台可按活动规则设置有效期。
- 月度套餐额度按订阅周期发放，周期结束未使用额度默认失效，不跨周期结转；若平台后续需要结转，作为单独套餐属性开启。
- 用户充值余额默认长期有效，退款只处理未消费部分。
- 同一用户可叠加多个套餐；每个套餐权益独立建账、独立到期，不能把不同模型/媒体单位混成一个额度池。
- 套餐到期、取消或退款时，已产生的消费不回滚；未消费权益按套餐规则失效或退回，佣金同步冲正。

### D22. 自动续费失败、宽限期与停服：已确认

- 到期日、+1 天、+3 天、+5 天自动重试扣款，续费失败进入 `past_due` 并通知用户和所属渠道。
- 7 天宽限期内不发放新的套餐额度；原有未使用权益仍按原到期规则处理，不因宽限期无限延长。
- 宽限期内用户仍可使用现金余额，但不允许套餐或钱包透支。
- 7 天内仍未支付，订阅变为 `cancelled`，停止套餐权益和后续自动扣款。
- 之后重新支付按新的支付时间开启新周期，不追收失败期间的套餐费用；已产生的 API 消费照常结算。

### D23. 平台后台角色与权限：已确认

已确认平台内部后台及终端侧采用以下角色拆分：

- 平台超级管理员：全局配置、Provider/模型、路由、渠道、套餐、权限和紧急操作。
- 财务管理员：充值、退款、授信、额度调整、佣金结算和对账；不能查看上游密钥明文。
- 运营管理员：模型上下架、套餐审核、内容/风控策略和用户运营；不能直接改账务余额。
- 技术/值班管理员：Provider 凭据、健康检查、路由和故障处理；不能退款或发放额度。
- 渠道管理员：仅管理本渠道用户、套餐、推广链接和数据；不能查看其他渠道或平台成本。
- 只读审计角色：查看报表和审计日志，不能执行写操作。
- 普通用户（唯一终端用户类型）：使用平台 Token/API 的一方，只能查看和管理自己的余额、套餐、用量、账单、API Key、媒体任务和个人设置。平台/财务/运营/技术/渠道管理员是叠加在账号上的管理角色，不是另一类终端用户。

推荐所有高风险操作（退款、手工加款、佣金调整、修改 Provider 凭据、改价格底线）启用二次确认并记录审计日志。

终端用户不能查看 Provider 密钥、平台成本、其他用户数据或分销佣金；通过渠道注册的用户不能自行切换渠道归属。

### D24. Provider 管理字段与健康检查：已确认

推荐 P0 为每个 Provider 保存：名称、类型、协议适配器、API 基址、凭据引用、支持模型映射、区域、优先级/权重、超时、重试和熔断参数、并发/RPM 限制、能力标签、维护状态、成本价版本、最近健康状态和审计信息。

健康检查采用轻量探测与真实请求指标结合：定时检查鉴权和模型可用性，实时记录成功率、错误码、P50/P95 延迟、429/5xx 比例和最近心跳；状态分为 `available`、`degraded`、`unavailable`、`maintenance`。连续失败触发熔断，恢复需连续成功探测后自动或人工解除。

已确认：默认不发送会计费的探测请求，优先使用 Provider 的模型列表、健康接口、鉴权检查或能力查询接口；无健康接口时，只有管理员显式开启才允许极小文本探测，禁止用视频/图片生成任务做自动探测。真实业务请求指标作为主要健康依据，连续失败自动熔断，恢复需连续成功探测或真实请求后再恢复。

指标必须同时满足运维和运营分析：按 Provider、模型、渠道、代理商、用户和 API Key 维度记录请求量、成功率、错误码分布、429/5xx、超时、重试/fallback 次数、P50/P95/P99 延迟、Token/媒体用量、客户收入、上游成本、毛利、预授权失败、待对账量和回调延迟；支持时间序列、告警阈值、日报/账期汇总和导出。

### D25. P0 数据模型与 API 契约：已确认

推荐先冻结核心实体：用户/角色、渠道组织、归因关系、Provider、模型、路由组、API Key、套餐/订阅、钱包与额度账户、充值订单、usage/attempt、账务流水、佣金流水、媒体任务、审计日志。所有余额和额度以流水为准，汇总字段只能做缓存。

对外 API 以 OpenAI 兼容接口为主，同时提供媒体异步任务、用量查询、账单和 Provider 选择参数；错误码、幂等键、request_id/attempt_id 和分页格式统一。

已确认先以“数据库表设计 + OpenAPI 契约 + 关键状态机”作为交付物，再进入技术选型和开发拆分；对应文档见 `05-TokenHub-P0数据模型与状态机.md` 和 `06-TokenHub-P0-OpenAPI契约.md`。

### D26. P0 系统架构形态：已确认

- P0 采用模块化单体 + 异步 Worker，不一开始拆分微服务。
- PostgreSQL 作为账务和核心业务数据库；Redis 用于限流、并发控制、短期缓存和分布式锁；对象存储保存媒体素材。
- API Gateway、管理后台、用户充值站点可按域名和模块隔离，底层先保持同一业务系统。
- 后端尽量复用 Bifrost 的 Provider 适配、协议转换、路由、重试、流式和观测能力。

### D27. Bifrost 集成部署方式：已确认

推荐 P0 采用“TokenHub 控制面 + Bifrost 数据面”的独立内部服务/Sidecar 方式：TokenHub 负责认证、渠道、权限、预授权和最终账务，Bifrost 负责协议适配、Provider 路由、重试、流式透传和基础指标；通过内部 API 传递 `request_id`、`attempt_id` 和业务 metadata。

同时保留 `GatewayAdapter` 接口，未来若后端采用 Go 且需要降低网络跳转，再评估嵌入 Bifrost SDK。Seedance 等 Bifrost 未覆盖的媒体生命周期能力由 TokenHub Media Worker 直连 Provider Adapter，不能让 Bifrost 成为账务唯一事实源。

已确认采用“P0 独立 Bifrost 内部服务/Sidecar，TokenHub 通过适配器调用；未覆盖能力由 TokenHub 自己补齐”的部署边界。

### D28. 技术栈与异步任务基础设施：已确认

推荐：

- 后端使用 Go，与 Bifrost 原生生态和 SDK 方向一致；
- HTTP API 使用标准 Go Web 栈，业务按模块化单体组织；
- PostgreSQL 作为核心数据库，Redis 负责限流、短期状态和锁；
- 异步任务采用“领域事件 + PostgreSQL Outbox”设计；P0 可先由 Worker 轮询任务表执行，并定义 Dapr Pub/Sub 兼容的 CloudEvents 事件格式。若部署环境已具备 Dapr，再接入 Dapr sidecar；后续拆分微服务时可直接复用 Pub/Sub、Service Invocation、State/Secrets 等抽象，而不改业务事件契约。
- P0 不强制引入 Dapr Workflow；媒体轮询、支付 webhook、usage 对账和佣金结算先使用可观测的任务表/Worker，复杂编排稳定后再评估 Workflow。
- 对象存储使用 S3 兼容接口；
- 管理后台和用户站点使用 React/Next.js 或同等前端栈，共享品牌和权限组件；
- 监控使用 Prometheus + Grafana，日志使用结构化 JSON，链路使用 OpenTelemetry。

已确认采用“Go + Gin 后端、PostgreSQL + GORM、Redis + Outbox Worker（Dapr 兼容、可选 sidecar）+ S3 对象存储 + React/Next.js 前端”的 P0 技术栈；日志使用 zerolog，配置使用 Viper，监控使用 Prometheus + Grafana，链路使用 OpenTelemetry。

GORM 使用约束：钱包、预授权、usage、退款、佣金等账务核心必须显式开启事务、使用行锁/乐观锁、建立唯一幂等索引和定点金额字段；生产环境使用版本化 migration，不使用 `AutoMigrate` 直接改表。

### D29. 部署演进路线：已确认

- P0 使用 Docker Compose 或单节点容器部署，核心依赖使用独立服务。
- 架构从一开始遵循 Dapr 兼容的事件和服务边界，但不强制 P0 运行完整 Dapr Runtime。
- 规模增长后迁移到 Kubernetes，并逐步启用 Dapr sidecar、Pub/Sub、Service Invocation、State 和 Secrets。
- 迁移过程中不改变客户 API、账务流水、领域事件和异步任务幂等契约。

### D30. P0 开发拆分与交付顺序：已确认

推荐按纵向切片交付：M0 基础工程与安全 -> M1 身份/渠道/品牌 -> M2 Provider/模型/Bifrost 文本网关 -> M3 钱包/预授权/usage -> M4 Seedance 媒体 -> M5 套餐/订阅/支付 -> M6 分销/佣金 -> M7 运营运维与上线加固。M3 完成前不接入真实客户流量；M4/M5/M6 可并行，但共享账务、幂等和审计底座。

每个里程碑同时交付代码、数据库 migration、API 文档、配置示例、单元/集成/端到端测试和回滚说明。详细范围和验收标准见 `08-TokenHub-P0开发拆分与验收顺序.md`。

已确认按这套 M0-M7 顺序推进 P0 开发。

### D31. 佣金冻结、结算与提现：已确认

推荐默认规则：

- 佣金基于已确认 usage 产生后进入 `frozen`；冻结期建议为 7 个自然日，用于处理退款、争议、异常 usage 和风控复核。
- 冻结期结束自动变为 `available`，按月生成结算单；结算单需绑定 policy version、usage 明细、归因和冲正记录。
- P0 先支持平台人工审核后打款/人工入账，不直接接入自动代付；自动打款列为后续能力。
- 平台可设置最低结算金额，未达到门槛的可结转到下个周期；封禁、退款或违规时可冻结或冲正未结算佣金。
- 渠道和 KOL 只能查看自己范围内的佣金明细、冻结原因、可结算金额和结算单，不能修改佣金比例。

已确认采用“7 天冻结 + 月度结算 + P0 人工打款/入账 + 可配置最低结算金额”的佣金规则。

### D32. P0 生产可靠性与灾备：已确认

推荐默认目标：

- PostgreSQL 每日全量备份 + 持续 WAL/PITR，备份加密并异地保存；至少保留 30 天。
- P0 目标 RPO ≤ 15 分钟、RTO ≤ 1 小时；每季度至少演练一次恢复。
- Redis 不作为账务事实源，丢失后可重建限流、缓存和短期锁状态。
- 对象存储启用版本/生命周期策略；媒体结果按 7 天清理，审计和账务数据不随媒体清理。
- Provider 故障时允许切换 fallback；账务数据库故障时停止新请求和充值发放，避免产生无法对账的消费。
- 支付 webhook、媒体回调和 usage 对账任务必须可重放；恢复后按事件幂等补处理。

已确认采用“RPO 15 分钟、RTO 1 小时、每日备份 + PITR、季度恢复演练”的 P0 可靠性目标。

### D33. 界面数量、门户和权限显示：已确认

推荐采用“一个前端代码库 + 三个权限门户 + 一个公共站点”：

1. 公共/充值站点：品牌首页、登录注册、模型/套餐展示、充值和订阅购买；按域名加载平台或 OEM 品牌。
2. 普通用户控制台：余额、套餐/订阅、API Key、用量、账单、媒体任务、文档和个人设置。
3. 渠道/代理控制台：本渠道用户、套餐、推广链接、归因、额度、用量、佣金和结算；代理商/KOL 按层级看到不同数据范围。
4. 平台管理控制台：Provider、模型、路由、价格、支付、渠道、套餐审核、账务、佣金策略、指标、审计和系统设置。

实现上可以是同一个 React/Next.js 应用，通过域名、登录角色和 scope 选择门户及菜单；但隐藏菜单只是体验层，后端 API 必须再次校验角色、渠道和资源范围。敏感字段按门户强制隐藏：终端用户/渠道看不到 Provider 密钥、平台成本和其他渠道数据；分销角色看不到 prompt/completion 原文；平台财务可看账务但不能默认读取上游密钥；技术角色可管理凭据但不能退款或改佣金。

已确认采用“一个前端代码库、公共站点 + 用户控制台 + 渠道控制台 + 平台管理控制台”的界面方案；前端按角色/域名显示，后端按 RBAC + 渠道 scope 强制校验。

### D34. 开发者文档与 API 接入中心：已确认

推荐纳入 P0：

- API 变更按版本管理，旧版本文档保留，废弃接口提前通知。

已确认将“公共开发者文档 + 用户专属接入示例 + OEM 品牌化文档”纳入 P0。

### D35. 前端技术栈：已确认

- Next.js + TypeScript，共享公共站点、用户控制台、渠道控制台和平台管理控制台代码库。
- Tailwind CSS + shadcn/ui/Radix UI，使用 CSS Variables 和 Design Tokens 支持 OEM 主题。
- Zustand 只管理客户端交互状态；TanStack Query 管理余额、账单、Provider、模型和指标等服务端数据。
- React Hook Form + Zod 处理表单和前端校验；TanStack Table 处理管理后台数据表格；Apache ECharts 处理运营/运维看板。
- 通过 OpenAPI 生成 TypeScript Client；接口契约变更必须同步生成客户端类型。
- next-intl 预留中文、英文和日文；Vitest/Testing Library/Playwright 覆盖单元、组件和端到端测试。
- Web 控制台认证使用 HttpOnly/Secure Cookie，不将登录凭据放入 localStorage；前端隐藏菜单不代替后端 RBAC 和渠道 scope 校验。

### D36. 后端框架与基础库：已确认

- HTTP 框架使用 Gin；
- 日志使用 zerolog，统一 JSON 字段和 request/attempt trace 字段；
- 配置使用 Viper，明确环境变量覆盖层级，敏感配置只引用密钥管理系统或加密值；
- 数据库使用 PostgreSQL + GORM；
- GORM 业务模型与账务模型分层，账务核心禁止隐式 save、无条件 update 和生产 AutoMigrate；
- migration 使用版本化脚本，关键约束（唯一幂等键、金额精度、外键、状态枚举）在数据库层落地。

### D37. 微服务演进约束：已确认

- P0 虽采用模块化单体，但按未来服务边界组织代码：identity/access、channel、catalog/routing、gateway、billing/entitlement、payment、media、commission、audit/observability。
- 每个模块拥有自己的表和 repository；模块之间只能通过 service interface、DTO 或领域事件交互，禁止跨模块直接读写表和共享 ORM model。
- P0 可共用一个 PostgreSQL 实例，但按模块 schema/表前缀和独立 migration 管理数据所有权；未来拆服务时迁移对应 schema，不改变领域事件和 API 契约。
- 跨模块流程使用 Outbox + CloudEvents + 幂等消费者；不依赖分布式事务，退款/冲正/佣金等采用补偿事件。
- 推荐拆分顺序：media worker、payment webhook、usage reconciliation/commission worker、observability，再评估 gateway 和 billing；账务核心最后拆分。
- 服务间统一 request_id、trace_id、tenant/channel scope 和事件版本；Redis key、配置、密钥和指标命名按服务隔离。
