# 账本、模型调用与运行验证证据

更新：2026-10-16。对应新业务实现，不包含旧业务或数据兼容。以下分别记录代码、实际运行结果和验证边界，不能据此推断整个产品已经完成验收。

## 实际验证环境

数据库为独立 PostgreSQL 16。测试在 `tokenhub_financial_drill_20261016_a` 内创建并清理自己的随机 schema，不使用运行环境的数据。模型流量由实际 Bifrost 发往仓库外 `../integration-lab` 的 HTTP/SSE 服务；临时结果经实际加密和私有 MinIO，限流使用实际 Redis。接口故障由独立协议服务产生，没有用业务服务内部的固定返回值代替这些联调。

这些结果证明产品与声明的协议契约能够协作，不能代替供应商真实模型的参数、用量、上界、稳定性或商户实账验收。

## 资产与计费规则

- **A114、A115：正式注销的赠送失效。** `ledger.CancelClosureGifts` 只供已认证的注销协调器在关闭同一事务内使用：剩余购买来源未归零或仍有占用时拒绝，纯赠送无需另行购买额度放弃；不改现金和佣金。实际 PostgreSQL `-race` 专项 2.099s 通过，核对 7 ATG 赠送仅撤销一次、11 USD 不变、外层失败全部回滚及有偿基数为零。停止使用和开始注销阶段不调用此操作。
- **A009：资产隔离。** `ledger/service.go` 和资产命令校验经营方、所有者和单位，没有通用客户间转账接口。`TestUnitAndScopeAreNotInterchangeable` 验证单位及主体不能混用；真实渠道接管是有原始记录的一次受权转移。
- **A035、A060：周期。** `ledger/calendar.go` 保留套餐日历到期和 Key 自然窗口两种语义，月末、闰年、季度、年和不限期由 `TestCalendarClampsAndNaturalWindows` 验证。请求持久化受理窗口，跨期完成不能改归属；重置 Key 不清预算。
- **A036：额度扣减顺序。** `ledger/grants.go` 按到期、开始时间和唯一标识稳定排序，同来源批次购赠同比例分摊。`TestGrantConsumptionExpiryPaidBasisAndRetries`、`TestGrantFEFOAndUnfundedShortfall` 和跨 64 项分页测试核对总额、实付基数和余数。不锁定无关的后序额度。
- **A038：到期和在途占用。** 到期操作仅处理未占用剩余量；已受理请求保留原占用，完成或释放后再处理到期。账本到期与真实 usage 释放/结算均走同一命令，重复处理不会二次扣量。
- **A046、A048：余额和并发。** `usage/admission.go` 先原子占用再调用。`TestPostgresConcurrentSharedPoolAndUnknownUsageFinality` 验证两个 Key 竞争一个账户，余额仅容纳一个请求时只放行一个；账本另有并发扣款、占用捕获、事务回滚和不能挪用其他占用的测试。持续负载结果见下文。
- **A047、A049：逐层采购。** 每条供货边按已核实最大责任预占，实际结算只扣实际金额并释放差额。四条销售链的实际 Bifrost 联调分别核对平台、OEM 和渠道余额；增加了逐层耗尽采购余额后拒绝调用、回滚其他层占用的专项。
- **A050、A051：超预估。** `TestPostgresActualOverageNoCustomerDebtAndKeyResetPreservesBudget` 使用 Key 上限 0.6、账户 0.7、实际 0.8，核对 Key 超额 0.2、账户实扣 0.7、经营方缺口 0.1；缺口不进入佣金基数。后续充值不会补扣这笔缺口。
- **A052：受理价格。** `usage/settlement.go` 和供应成本记录读取不可变受理快照；目录测试核对各供货边快照。实际流式故障转路由测试在输出过程中调高供应商价格，要求该请求仍按原价记成本。
- **A053、A055、A056：取消、断线和用量未知。** 独立 SSE 实测覆盖成功、收到可靠用量后客户断开、上游输出后断开、终止流但缺少用量。只有可靠用量收费；缺失用量到期释放，迟到用量不能再次扣款；已有输出后不启用备用路由重新生成。此次实测发现并修复 Bifrost 合成全零用量被误认作可靠证据的问题。
- **A054：内部失败重试。** `usage/execution.go` 将所有尝试归于一个请求，客户和采购只结算一次，每次真实尝试成本独立保留。故障路由明确返回 429、备用同模型成功的实际测试要求一笔客户费用，未知失败成本保留待核实，重复客户请求不再生成。503 或提交中断可能已经执行，按结果未知处理，不能套用明确拒绝的重试规则。
- **A057：异步。** 视频实际提交、等待、查询、完成和两次下载已通过；按原任务标识查询，只收一次 0.04 ATG。查询与下载 URL 使用 `{task_id}` 模板并安全编码，不能将任务标识注入域名、查询参数或路径。无原任务证据时不重新提交生成，核实超时免费；不存在“查不到就再生成”的恢复路径。
- **A058：幂等。** 请求内容指纹、Key 和业务键共同约束重复提交；异内容冲突。真实 HTTP 重试从私有临时结果回读，不产生第二次尝试；结果清理后原财务状态保留，不重新生成。
- **A059、A061：Key。** Key 不分配资产；预算、模型、频率和并发只限制准入。真实 Redis 专项覆盖并发、配置重置、Redis 故障与数据库计数的交叉验证。旧密钥重置后失效，历史费用和占用保留；已受理请求不因 Key 更新而失去结算依据。
- **A062：权限。** Key 只用于模型调用，同品牌他人任务仍拒绝。四链测试验证跨品牌 Key 无效；异步真实测试验证他人下载拒绝。用户页面采用零售账单 DTO，不直接序列化供货快照。登录和资金 API 的越权由 Portal 专项覆盖。
- **A079、A080：错误扣费。** `ledger/corrections.go`、`usage/corrections.go` 按原实际扣款、原来源、原预算和原实付基数冲正。过期额度不恢复可用期限；正常供应商成本不能因零售纠错自动冲回。并发纠错不能超过原可纠正金额。
- **A107—A109：接管连续性。** 实际完成渠道接管后使用原 Key 调用 Bifrost，扣减承接权益，保留原实付基数；后续成本归品牌，旧渠道无新流水，一次承接价不随实际使用改变。接管退款、采购抵扣和资金缺口另见经营与资产证据。
- **A118：保留。** 私有结果先删除对象再删除引用，账务继续保留；同步短期回读和异步结果均不提供长期会话历史。真实 MinIO 测试验证权限、密文、重复回读、到期删除及生命周期配置，异步下载不延长保留期。
- **A122—A125：账单和经营口径。** `FinancialFacts` 区分有偿调用、赠送履约成本、冲正、真实供应成本及待核实成本；赠送成本只是总成本子集。真实历史快照验证接管与纠错不会倒改旧期末。用量导出仅展示本经营方履约成本，下级不得取得平台真实供应商价格；财务报告权限和票据由 operations/portal 证据补齐。
- **A126、A127：精度。** Decimal 和有理数计算使用 18 位内部小数，分摊属性测试、低于最小记账单位的持续余数及冲正回滚验证守恒。前端显示值不参与后台足额判断。实际浏览器账单已展示购赠比例分摊，避免误把 ATG 面值当成 USD 实付。

## 持续负载与峰值

硬件为 Mac15,7，12 个 CPU、18 GiB 主机内存；Docker 分配 12 个 CPU、9,434,566,656 字节内存。运行时还有其他集成测试和构建，属于共享开发机验证，不能作为独占服务器容量报告。单测试最多 32 个数据库连接；100 个调用协程和 50 个购买协程共用一个客户，特意造成账户热点。购买协程每笔完成后等待 2 秒，调用协程持续发起；没有宣称 150 个独立经营方。

30 分钟测试完成 39,914 次调用、23,474 笔购包。失败、未完成请求、重复上游尝试、分录不平衡、余额投影差异和残留占用差异均为零。调用 p95 为 8,879.093ms，订单 p95 为 3,766.603ms，这两个值包含排队及外部 I/O。取得初始业务锁后，受理处理 p95 为 34.250ms，结算处理 p95 为 20.035ms；该分段不含提交，也不代表整段平台开销已满足 200ms 目标。

随后补入 `usage.admit.committed_work` 和 `usage.settle.committed_work`，从取得初始业务锁一直测到事务提交或回滚完成；只在方法自己拥有事务时产生该分段，不把调用方尚未提交的事务算成已提交。60 秒诊断完成 2,714 次调用、1,054 笔购包，失败和上述对账异常均为零，包含提交的受理/结算 p95 分别为 **7.677ms / 14.445ms**。含排队的完整受理/结算 p95 仍为 **920.383ms / 917.591ms**，整次调用 p95 为 3,575.321ms。此短测解释了热点锁排队与账务处理的区别，不把一分钟结果替换成三十分钟持续性能结论。原始结果保存为仓库外 `../integration-lab/evidence/load-commit-20261016.json`。

定位发现无限预算 Key 仍在每次受理时汇总全部历史请求，已经移除这项不必要查询；有预算 Key 保留原校验。随后 200 个调用、100 个购买协程持续两分钟，完成 4,588 次调用、3,383 笔购包，各项错误和账差仍为零。调用 p95 为 8,465.065ms、订单 p95 为 3,194.480ms；锁后受理 p95 为 5.912ms、结算为 12.698ms。两次数据规模和代码不同，不能用它们推导线性扩容比例。

这轮说明资金正确性在上述负载下保持，同时单账户热点存在显著排队。正式商业容量需要在目标部署硬件、真实模型延迟、实际经营方分布和数据库规模下测定。原始报告位于仓库外 `integration-lab/evidence/load-sustained-20261016.json` 和 `load-burst-20261016.json`。报告多出的一个计费 span 来自测试初始化，不计入负载调用数。

## 实际容器、HTTPS 与恢复

API、worker 和 migrate 从实际 Dockerfile 构建，在独立新库和私有桶中启动。Compose 的 exec 健康检查、真实数据库/Redis/S3 readiness 均通过。Caddy 连接实际 API，在本地隔离 CA 下完成证书链和主机名校验；未登记 SNI 被拒，两个 metrics 路径返回 404，readyz 返回 200。此次实际检查发现并修复 Caddy 的 respond/handle 排序造成指标接口未正确拦截的问题。

本地 CA 不等于公开 DNS 或公网证书已验证。最终业务修复后已重新构建 API/worker 和 Next 镜像并实际启动，首页及两条业务代理入口均返回 200；公开 metrics 为 404，未授权直接 metrics 为 403，未登记 SNI 的 TLS 握手被拒。最终镜像与结果见仓库外 `integration-lab/evidence/runtime-tls-final-20261016.json`；原阶段演练证据仍保留。

持久任务另有真实 OS 进程故障演练：测试子进程在业务效果未提交、效果已提交但任务未确认两个边界收到 SIGKILL；替代进程等待真实两秒租约到期，领取原任务并完成。两种情况都只保留一条业务效果，尝试次数为二，旧 fence 拒绝提交。没有修改数据库时钟假装过期。`TestPostgresActualProcessLossReclaimsLeaseWithoutDuplicateEffect` 在真实 PostgreSQL 和 `-race` 下 8.472s 通过。这证明持久任务基础设施恢复；外部资金仍依靠原指令幂等和查单，不从数据库任务幂等推断外部转账只会发生一次。

备份使用实际 PostgreSQL 16 pg_dump、私有 S3 长期文件清单及独立密钥认证加密。隔离恢复后，高精度余额 123.456789012345678901 USD、占用 3.125 USD、分录及一个待办保持一致；五个源对象只恢复三个长期文件，模型临时结果和导出不进备份。损坏备份和已有恢复目标均拒绝覆盖，恢复不启动 worker。证据为仓库外 `integration-lab/evidence/backup-drill-20261016.json`。异地副本、正式密钥保管和恢复后真实通道对账仍属于部署配置条件。

全仓 `-race -p 1 -count=1 -timeout 15m` 后，对发现问题的完整包复跑，最新合并结果为 22 个有测试包、239 个顶层用例通过，含子用例共 308 项，无未解决失败。受影响包 commerce 52.548s、payments 6.160s、usage 106.508s、portal 73.269s。ledger 6.148s、jobs 9.050s、modelruntime 2.269s、backup 14.141s、remediation 228.888s 均在全仓轮次通过。

usage 整包包含四销售链逐边采购不足、流式可靠用量/断线/备用路由、异步原任务和私有结果过期删除。最终修复 Key 创建取主机时间、受理取数据库时间造成刚创建即被判早于创建时刻的问题；API 和网页体验 Key 及当前预算展示统一取数据库业务时钟。portal 签名回调→余额充值→购包→模型调用综合用例 9.580s 实际通过，旧环境变量缺失不再让标准外部测试入口跳过它。

回归还修复支付事实回放复用 JSON 缓冲造成证据损坏、经营概览未结责任查询缺少外层事务；commerce 发票用例的即时消费时间改取真实数据库时钟。上述修复后的整包结果取代原失败结果，原失败事实未删除。只有普通入口的负载用例和子进程 helper 有说明性跳过：负载已单独运行，helper 由父用例启动。
