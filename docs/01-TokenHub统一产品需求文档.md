# TokenHub 统一产品需求文档

版本：0.1
状态：讨论稿
关联：`docs/00-TokenHub调研与产品结论.md`、`docs/02-分销与代理商需求.md`、`docs/04-TokenHub逐项讨论清单.md`、`docs/05-TokenHub-P0数据模型与状态机.md`、`docs/06-TokenHub-P0-OpenAPI契约.md`、`docs/07-TokenHub-Bifrost集成边界与架构建议.md`、`docs/08-TokenHub-P0开发拆分与验收顺序.md`

## 1. 目标与成功标准

### 1.1 业务目标

1. 平台管理员能够接入多个模型提供商，维护模型目录、上游模型映射、成本价和销售价。
2. 终端用户只需一个 API Base URL 和 API Key，即可调用多个模型，并获得稳定、可解释的路由和 fallback。
3. 每次请求都能追溯到租户、用户、API Key、渠道、提供商、模型、价格版本、token usage 和账务流水。
4. 平台可以通过预付余额、额度、限流和熔断控制坏账及上游风险。
5. A/B/C 渠道可以在权限隔离下发展代理商和 KOL，并根据实际 API 消耗产生可审计佣金。

### 1.2 可验证成功标准

- 新增一个提供商和一个模型映射后，终端用户可通过兼容 API 成功调用。
- 同一模型存在多个健康提供商时，路由可按配置顺序或价格/延迟策略选择，并记录候选与最终结果。
- 并发请求不能使用户、渠道或平台余额低于允许的透支阈值。
- 任意账单可以通过请求 ID、usage 事件和账务流水重算；重复 webhook 或重试不会重复扣款。
- 代理商只能看到自己数据范围内的用户、用量、佣金和结算记录。

## 2. 范围

### P0 必须交付

- 平台、渠道、用户、角色和权限基础模型。
- 提供商管理：API Key/OAuth 凭据、健康检查、能力和状态。
- 模型管理：模型目录、提供商映射、能力、成本价、销售价、版本。
- 统一 API 网关：OpenAI Chat Completions/Responses 兼容；流式输出；基础错误映射。
- 媒体任务网关：视频/图像/音频生成的异步任务、状态查询、回调、结果下载和媒体计费；P0 首先支持 Seedance 类视频模型。
- API Key 管理：创建、轮换、禁用、过期、来源和限额。
- 钱包与用量：预授权、usage 结算、余额流水、API Key 的 RPM/并发控制，以及 B/C 渠道消耗额度。
- 基础账单：充值订单、消费明细、退款/冲正、对账导出。
- 订阅与套餐：月度订阅、包月额度/Token、赠送额度、到期/续期和自动续费。
- 提供商路由：优先级、fallback、健康摘除、超时和重试策略。
- A/B/C 分销基线：归因、实际消耗计佣、冻结期、结算和数据隔离。
- Anthropic Messages 兼容适配器。
- Bifrost 集成：复用 Provider 协议适配、路由、重试、流式透传和基础观测能力；TokenHub 保留控制面和账务事实源。
- 运维与运营指标：Provider、模型、渠道、代理商、用户和 API Key 维度的请求、延迟、错误、usage、成本、收入、毛利和佣金指标。
- OEM 独立域名、API Gateway 域名、管理后台域名及 Logo/配色/站点品牌配置。
- 代理商 -> 1 级 KOL -> 2 级 KOL 的基础推广层级和数据隔离。
- 公共开发者文档、用户专属 API 接入示例和 OEM 品牌化文档中心。

### P1

- 复合模型组和模型别名。
- 提供商级数据策略、ZDR、区域和模型参数能力过滤。
- 更复杂的代理商等级、手动扣款和高级分销策略。
- 高级运营报表、预测分析和复杂异常告警编排。
- 用户/项目级 daily/weekly/monthly/lifetime 预算、TPM 和更细粒度预算继承。
- 企业级多层预算继承、复杂组织配额策略。

### P2

- 平台代扣代发自动化。
- BYOK、更多协议、媒体模型扩展、发票和企业合同。

### 明确不做

- 无限级代理树。
- 第一版自动对外提现/打款。
- 复杂 CRM、工单、合同、发票系统。
- 多推广来源拆分归因。
- 以真实毛利润实时分成替代可解释的消耗计佣。

## 3. 用户与角色

| 角色 | 数据范围 | 核心操作 |
| --- | --- | --- |
| 平台管理员 | 全平台 | 提供商、模型、全局价格、渠道、风控、账务、审计 |
| 平台运营/财务 | 按授权模块 | 查看报表、审核充值/退款/结算、导出对账 |
| A 平台直推管理员 | A 渠道 | 管理下级代理商/KOL，查看 A 渠道数据 |
| B/C 批发商管理员 | 自有渠道 | 预充值、下级管理、渠道价/佣金配置、结算方式 |
| 代理商 | 自己及直接推广数据 | 推广链接、发展 1 级 KOL、查看佣金 |
| 1 级 KOL | 自己及 2 级 KOL 业绩 | 推广、发展 2 级 KOL、查看佣金 |
| 2 级 KOL | 自己直接推广数据 | 推广、查看佣金 |
| 终端用户/开发者 | 自己 | 充值、API Key、预算、用量、账单 |

权限必须拆分为“功能权限”和“数据范围”。后端每个查询必须带租户/渠道 scope，不能仅依赖前端隐藏按钮。

## 4. 提供商管理

### 4.1 提供商实体

字段至少包括：名称、slug、提供商类型（direct/aggregator）、协议类型、Base URL、认证方式、凭据引用、区域、数据训练/保留策略、支持模型、状态、健康状态、权重/优先级、超时、重试和备注。

P0 首发媒体上游为火山方舟直连和 OpenRouter。聚合提供商必须声明最终上游是否可见；若无法取得最终 provider、usage 或价格明细，只能按已配置的保守计费策略进入待对账，不能伪造精确成本。路由器必须阻止聚合提供商回流 TokenHub 自身。

提供商认证凭据只保存密文引用或加密密文；列表和日志中只显示脱敏指纹。禁止把上游完整 Key 写入普通请求日志。终端用户 API Key 按用户要求支持长期查看，采用“加密密文 + hash 索引”双存储。

### 4.2 上游账号池

一个提供商可以有多条账号/Key。每条账号记录：

- 账号类型：API Key、OAuth、其他适配器专用凭据。
- 适用模型/模型标签。
- 并发、RPM、TPM 或提供商声明的额度。
- 当前状态：active、disabled、cooldown、invalid、exhausted、unknown。
- 最近成功、错误、429、401、403、延迟和冷却截止时间。

### 4.3 健康检查与摘除

- 主动探活只验证连接和认证，不默认产生计费请求。
- 真实请求结果更新健康统计。
- 401 暂停并要求重新认证；403 记录权限/权益问题；429 使用 `Retry-After` 或配置冷却；5xx 和超时进入指数退避。
- 熔断器打开时，请求应快速失败或进入备用提供商，不继续打爆故障账号。

## 5. 模型管理

### 5.1 客户模型目录

模型需要有平台稳定的 `public_model_id`，与上游 `provider_model_id` 解耦。字段至少包括：

- 展示名、厂商、版本、模态、上下文长度、最大输出。
- 支持的参数：tools、vision、json、reasoning、streaming 等。
- 输入、输出、缓存读、缓存写、reasoning、按请求和媒体单位价格。
- 可见性、上线/下线时间、废弃时间、替代模型。
- 模型别名、默认路由组、备用模型列表。

### 5.2 价格版本

价格必须带生效时间和版本号。新价格只影响新请求；历史请求保存价格快照。对于长上下文、峰谷时段等条件价格，使用可扩展的 price rules，而不是修改历史单价。

提供商模型和价格支持定期自动同步，但同步结果必须先进入 `draft`，经管理员审核后发布到客户模型白名单。模型下线进入 `deprecated`，不得删除历史映射和价格版本；管理员可以手工覆盖同步结果。

### 5.3 模型-提供商映射

映射记录包含：public model、model vendor、routing provider、upstream model、协议适配器、参数能力、成本价来源、可用区域、排序、最大并发和状态。一个公开模型可以映射多个路由 Provider；一个 Provider 也可暴露多个模型。`openai/gpt-5.6` 这类公开模型 ID 表示模型厂商和模型，不等同于实际承载请求的路由 Provider。

模型授权链路为：`routing_provider -> provider_model -> platform_enabled_model -> channel_entitlement -> api_key_model_allowlist`。Provider 下可以发现很多上游模型，但只有平台启用的模型才进入平台目录；渠道再从平台目录中选择允许销售/展示的模型；用户 API Key 可进一步收窄范围。Provider-model 映射本身也必须支持停用、价格版本、能力和健康状态。客户目录同时展示模型厂商和可用 Provider 状态，默认由平台自动路由。

### 5.4 媒体模型能力

媒体模型必须显式声明 `output_modality`（video/image/audio）、任务模式（sync/async）、输入模态（text/image/video/audio）、支持的分辨率、宽高比、时长、帧率、音频开关、参考素材数量和素材大小限制。不能仅用聊天模型的 `supported_parameters` 表示媒体能力。

Seedance 类模型至少需要支持：文生视频、图生视频、首帧/首尾帧、参考图/参考视频/参考音频、原生音频开关、时长、分辨率、宽高比和帧率。若上游声明支持，P0 同一任务模型还可提供视频编辑/延长。图像生成/编辑纳入 P0；独立音频生成、语音转写、视频理解和复杂视频时间线编辑放到 P1。不同版本的能力和价格必须由模型目录声明，不能在网关代码中写死。

## 6. 路由与网关

### 6.1 请求生命周期

1. 解析 API Key、用户、渠道和权限。
2. 校验模型可见性、参数能力、预算、余额、并发和速率。
3. 根据路由组筛选健康提供商和账号池。
4. 预授权预计金额或配置的保守上限。
5. 调用上游，支持 SSE 流式透传和客户端中断。
6. 解析上游 usage；结算实际金额；释放预授权差额。
7. 记录请求、尝试、上游响应摘要、用量、价格版本和账务事件。

### 6.2 路由策略

第一版支持：固定优先级、权重、价格优先、健康优先、手动 provider.only/provider.ignore、模型 fallback。后续再支持吞吐/延迟分位数、数据策略和区域策略。

同一业务请求的 fallback 不能重复收取客户费用；但每次产生的上游真实成本都必须记录，平台成本报表按尝试维度统计。

Seedance 默认火山方舟直连优先、OpenRouter 备用；跨模型 fallback 必须显式配置。流式响应开始返回正文后不切换提供商。异步媒体任务在上游已返回任务 ID 后不自动重复提交，未知状态进入待确认/对账。

### 6.3 兼容协议

- P0：`/v1/chat/completions`、`/v1/responses`。
- P0：`/v1/messages`（Anthropic 兼容）。
- 必须透传或明确处理：stream、tool calls、JSON schema、vision、reasoning、usage。
- 不支持的参数要返回结构化 4xx，而不是静默丢弃。

### 6.4 媒体任务 API

P0 提供 OpenAI 风格的异步视频接口：

- `POST /v1/videos`：创建任务，返回 `202 Accepted`、任务 ID、状态和查询地址。
- `GET /v1/videos/{id}`：查询 queued、in_progress、completed、failed、cancelled、expired 状态和进度。
- `GET /v1/videos/{id}/content`：下载或重定向到带过期时间的签名 URL。
- 创建时支持 `callback_url`；回调必须签名、幂等并可重试。
- P0 同时预留图像/音频任务的统一内部接口，具体公开路径按适配器能力启用。

媒体任务必须支持客户端幂等键、取消、超时、最大排队时长、结果保留期限、素材 URL/上传引用和内容安全失败原因。提交任务时先按“最大可能费用”预授权，任务完成按实际计费单位结算；明确失败且上游未产生费用时释放预授权。

## 7. 用量、额度与计费

### 7.1 额度层级

第一版只支持三类控制：

- 用户余额：请求前预授权，余额不足返回 `402`。
- API Key：禁用、过期、RPM 和并发限制；限流返回 `429`。
- B/C 渠道：按渠道批发价累计 API 消耗设置额度；超额后暂停该渠道新请求。

平台管理员仍可看到全平台成本和额度风险，但不在 P0 引入 workspace/project 多层预算、复杂继承、TPM 或 lifetime 预算。并发预授权要有过期回收任务。

### 7.1.2 订阅与套餐

P0 必须支持产品套餐、月度订阅、包月额度/Token、赠送额度和自动续费。平台提供基础模型能力、计费单位、批发成本、能力上限和风控规则；平台及 A/B/C/OEM 渠道都可以创建套餐。渠道套餐只能引用平台允许的模型和额度单位，并受平台设置的成本底线、额度上限和佣金约束。

渠道套餐发布采用“自动校验 + 风险人工审核”的折中流程：创建后自动校验价格底线、额度上限、模型权限、能力边界和风险规则；正常套餐直接发布，异常套餐进入平台审核。平台可随时下架、冻结或强制修改渠道套餐，但不得改写已经产生的订单和历史账单。

套餐应包含：名称、价格、币种、计费周期、可用模型/媒体能力、包含额度、超额单价、赠送额度、有效期、渠道可见范围、创建主体和续费策略。渠道可以自定义套餐组合、销售价和营销文案，但不能突破平台价格底线、成本规则或模型能力边界。

订阅权益与钱包余额分开记账，消费时按优先级扣减：即将过期的赠送额度 -> 当期套餐额度 -> 用户充值余额；具体优先级由平台配置。套餐额度必须支持文本 token 与媒体计费单位，不能只设计成单一 token 字段。已确认的默认规则是：赠送额度按有效期最短优先扣减并在到期后失效；月度套餐额度按订阅周期发放，周期结束未使用部分不结转；用户充值余额长期有效。多个套餐可以叠加，但各套餐权益独立建账、独立到期，并按模型/媒体计量单位分别扣减。套餐取消、到期或退款不回滚已产生的消费，未消费权益按套餐规则失效或退回，相关佣金同步冲正。

自动续费需要保存支付平台返回的支付方式引用，不保存银行卡完整信息。已确认续费失败处理为：到期日、+1 天、+3 天、+5 天自动重试，失败进入 `past_due` 并通知用户和所属渠道；7 天宽限期内不发放新的套餐额度，用户仍可使用现金余额但不允许透支；宽限期结束仍未支付则变为 `cancelled`，停止套餐权益和后续自动扣款。之后重新支付按新的支付时间开启新周期，不追收失败期间的套餐费用；已产生的 API 消费照常结算。

### 7.1.1 A 与 B/C 的额度路径

- A 官方渠道：终端用户直接充值，API 消费从自己的用户余额扣除。
- B/C 渠道：B/C 代理商先向平台充值，平台确认到账后按渠道价格政策形成可分配额度；代理商名下终端用户也必须充值，充值成功后按该代理商的销售价格/额度规则获得自己的服务额度。
- B/C 终端用户 API 消费从自己的已充值/已分配服务额度扣除，并归属于该代理商和渠道。
- 每次代理商充值、平台授予额度、终端用户充值、用户额度发放、回收、调整和消费都必须有独立流水；用户可用额度、渠道剩余额度和平台授信不能只存汇总字段。
- B/C 渠道额度是渠道风险上限，用户分配额度之和不得超过渠道可分配余额/授信。

### 7.2 用量事件

统一 `usage_event` 至少包含：request_id、attempt_id、tenant_id、user_id、api_key_id、channel_org_id、public_model_id、provider_id、upstream_model_id、prompt_tokens、completion_tokens、reasoning_tokens、cache_read_tokens、cache_write_tokens、media_units、unit_prices、amount、currency、occurred_at、idempotency_key。

上游没有 usage 时：默认不按猜测值扣款；按提供商适配器配置“拒绝结算、按预授权上限结算、异步补账”三选一，并在后台标记待对账。

### 7.3 客户账单

推荐公式：

`客户消费 = Σ(各计费项用量 × 销售价) + 请求/媒体费用`

每个请求只允许一个最终 customer_charge 事件；重复回调、重试或补账通过幂等键拒绝重复入账。

### 7.4 充值与退款

充值订单状态：pending、paid、failed、expired、refunded、partially_refunded。

P0 接入人工确认/兑换码、Stripe、支付宝和微信支付四类充值方式。核心统一处理充值订单、支付状态、验签、幂等、额度发放、退款和对账；适配器负责各支付平台的下单、查询、退款、webhook 和支付方式引用。支付平台 webhook 必须验签、幂等和记录原始事件。退款先冲减未使用余额，再按已消费部分生成负向账务和佣金冲正。自动续费按适配器能力处理：Stripe 支持支付方式引用和自动续费；支付宝/微信支付若当前商户资质或产品能力不支持自动扣款，则进入到期提醒和手动续费流程，不得伪造自动续费成功。

## 8. 分销与代理商

分销规则以现有 V2.1 为基线，详细字段和流程见 `docs/02-分销与代理商需求.md`。统一要求：

- 归因发生在注册成功时，OAuth 流程需暂存推广码。
- 佣金基数为实际 API 消耗的渠道批发价，不是充值额。
- 佣金按消耗事件产生独立流水，冻结期后可结算。
- 每笔消耗的直接佣金、代理商管理奖励、渠道佣金和团队奖励总和不得超过配置上限。
- 退款、人工改归因、手工结算和封禁都必须产生审计记录。

## 9. 管理后台

P0 导航：总览、提供商、模型、路由组、API Key、用户/项目、余额/充值、用量/账单、渠道/代理商、审计日志、系统设置。

后台按角色隔离权限：普通用户是唯一的终端用户类型，只能查看和管理自己的余额、套餐、用量、账单、API Key、媒体任务和个人设置；平台超级管理员、财务管理员、运营管理员、技术/值班管理员、渠道管理员和只读审计员是叠加在账号上的管理角色，不是另一类终端用户。平台超级管理员负责全局配置和紧急操作；财务管理员负责充值、退款、授信、额度、佣金和对账；运营管理员负责模型、套餐和风控运营；技术/值班管理员负责 Provider 凭据、健康检查和路由故障；渠道管理员仅能管理本渠道数据；只读审计角色只能查看报表和日志。普通用户不能查看 Provider 密钥、平台成本、其他用户数据或分销佣金，也不能自行切换渠道归属。退款、手工加款、佣金调整、Provider 凭据修改和价格底线修改等高风险操作必须二次确认并写入审计日志。

Provider 管理字段至少包括：名称、类型、协议适配器、API 基址、凭据引用、支持模型映射、区域、优先级/权重、超时、重试和熔断参数、并发/RPM 限制、能力标签、维护状态、成本价版本、最近健康状态和审计信息。默认不发送会计费的探测请求，优先使用模型列表、健康接口、鉴权检查或能力查询接口；无健康接口时，只有管理员显式开启才允许极小文本探测，禁止用视频/图片生成任务做自动探测。健康状态结合定时轻量探测与真实请求指标，记录成功率、错误码、P50/P95/P99 延迟、429/5xx 比例、超时、重试/fallback 次数和最近心跳，状态分为 `available`、`degraded`、`unavailable`、`maintenance`；连续失败触发熔断，恢复需连续成功探测或真实请求后自动或人工解除。指标按 Provider、模型、渠道、代理商、用户和 API Key 维度记录，并覆盖请求量、Token/媒体用量、客户收入、上游成本、毛利、预授权失败、待对账量和回调延迟，支持时间序列、告警、日报/账期汇总和导出。

### 9.1 Bifrost 集成边界

P0 采用“TokenHub 控制面 + Bifrost 数据面”：TokenHub 负责认证、渠道/模型权限、预授权、套餐权益、限流和最终账务；Bifrost 优先负责协议适配、Provider 路由、重试、熔断、流式透传和基础指标。TokenHub 通过受控内部 API 调用 Bifrost，透传 `request_id`、`attempt_id` 及用户/渠道/模型 metadata；Bifrost 的日志不能作为账务唯一事实源。Bifrost 未覆盖的 Seedance 异步生命周期能力由 TokenHub Media Worker 直连 Provider Adapter，并保持统一的客户 API 和账务结果。

### 9.1.1 界面与门户

P0 使用一个 React/Next.js 前端代码库，按域名、品牌、角色和数据 scope 渲染四类入口：公共/充值站点、普通用户控制台、渠道/代理控制台、平台管理控制台。公共站点支持平台和 OEM 品牌配置；用户控制台只展示个人余额、套餐、API Key、用量、账单和媒体任务；渠道控制台只展示所属渠道及授权层级的数据；平台控制台展示全局 Provider、模型、路由、价格、支付、渠道、套餐审核、账务、佣金、指标和审计。

前端菜单和字段按权限隐藏只是用户体验措施，后端每个 API 必须再次校验角色、渠道、资源 scope 和敏感字段策略。Provider 密钥、平台成本、其他渠道数据、prompt/completion 原文和分销佣金等信息不得因前端 URL、导出接口或 ID 枚举而泄露。

### 9.2 P0 技术栈与部署

- 后端：Go，模块化单体；
- 数据库：PostgreSQL，作为账务和核心业务事实源；
- Redis：限流、并发控制、短期缓存和分布式锁；
- 异步：PostgreSQL Outbox + Worker，事件采用 Dapr 兼容的 CloudEvents；
- 对象存储：S3 兼容接口；
- 前端：Next.js + TypeScript，共享公共站点、用户控制台、渠道控制台和平台管理控制台；Tailwind CSS + shadcn/ui/Radix UI 负责样式和组件，使用 CSS Variables/Design Tokens 支持 OEM 主题；Zustand 只管理客户端交互状态，TanStack Query 管理服务端数据；React Hook Form + Zod 处理表单，TanStack Table 处理后台表格，Apache ECharts 处理运营/运维看板；通过 OpenAPI 生成 TypeScript Client；next-intl 预留中/英/日国际化；Vitest、Testing Library 和 Playwright 覆盖测试。
- 观测：Prometheus + Grafana、结构化 JSON 日志、OpenTelemetry；
- P0 使用 Docker Compose 或单节点容器，后续迁移 Kubernetes + Dapr，不改变 API 和领域事件契约。

所有列表支持分页、筛选、导出和操作日志；敏感凭据不可回显。总览至少展示成功率、P50/P95 延迟、上游错误、平台成本、客户收入、毛利、余额风险、佣金负债和渠道消耗。

## 10. 非功能要求

- 安全：密钥加密、最小权限、2FA、敏感操作二次确认、审计不可删除、HTTPS、可信代理配置、URL allowlist。
- 可用性：提供商级超时/重试/熔断，Redis 只做短期状态，账务以数据库为准。
- 一致性：余额扣款和账务流水在同一事务边界内；跨服务事件使用 outbox 或等价可靠投递。
- 可观测性：request_id/attempt_id 全链路关联；指标、结构化日志和告警分离。
- 灾备：PostgreSQL 每日全量备份 + 持续 WAL/PITR，备份加密并异地保存至少 30 天；P0 目标 RPO ≤ 15 分钟、RTO ≤ 1 小时，每季度进行恢复演练。Redis 不作为账务事实源；支付 webhook、媒体回调和 usage 对账任务支持重放和幂等补处理。
- 隐私：默认不保存 prompt/completion 原文；若开启，按租户策略、保留期限和脱敏规则执行。
- 合规：对模型提供商服务条款、支付、跨境数据、代理分销和税务要求做上线前审查。

## 11. 验收重点

1. 价格切换后旧账单金额不变。
2. 并发双扣、重复 webhook、重复 usage 上报不会重复扣款。
3. 主提供商 429/5xx 时可以 fallback，并能区分客户请求成功与平台多次上游尝试成本。
4. 代理商无法通过改 URL 参数、导出接口或 ID 枚举读取其他渠道数据。
5. 退款会同时影响余额、消费账单、佣金状态和报表。
