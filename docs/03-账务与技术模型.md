# TokenHub 账务与技术模型

版本：0.1
状态：讨论稿

## 1. 设计原则

1. 账务流水不可变，余额是流水聚合/缓存，不是唯一事实。
2. 每个外部事件有幂等键；重试只重放，不重复入账。
3. 客户收费、上游成本、渠道佣金是三种不同账务事件，不能共用一个 amount 字段解决。
4. 金额使用定点 decimal，不使用浮点；每笔记录币种、汇率来源和价格版本。
5. 退款、冲正和人工修正使用反向流水，不覆盖历史记录。

## 3. 关键字段建议

### 3.1 request

`id`、`idempotency_key`、tenant/user/api_key/channel、public_model、requested_protocol、status、started_at、completed_at、final_attempt_id、customer_charge_id。

### 3.2 upstream_attempt

`id`、request_id、provider_id、account_id、upstream_model、attempt_no、status、http_status、error_class、latency_ms、ttft_ms、retry_after、provider_request_id、raw_usage_ref。

一次请求可有多个 attempt；只有最终 customer charge 一条客户消费事件，但成本报表要保留每次真实尝试。

### 3.3 media_task

`id`、request_id、tenant/user/api_key/channel、public_model、provider_id、upstream_task_id、task_type、status、progress、input_asset_ids、output_asset_ids、requested_duration、resolution、aspect_ratio、generate_audio、callback_url、expires_at、error_code、created_at、completed_at。

媒体任务和聊天请求使用同一账务链路，但任务状态是独立状态机：queued -> in_progress -> completed/failed/cancelled/expired。轮询和 webhook 都必须通过 `upstream_task_id + event_version` 幂等。

### 3.4 media_asset

`id`、task_id、asset_type、mime_type、size_bytes、storage_key、source_url_hash、checksum、signed_url_expires_at、retention_until、created_at。原始素材和生成结果默认进入受控对象存储，不把长期公网 URL 直接写入账单。

### 3.3 usage_event

`id`、request_id、attempt_id、usage_source、prompt_tokens、completion_tokens、reasoning_tokens、cache_read_tokens、cache_write_tokens、media_units、unit_price_snapshot、cost_amount、sell_amount、currency、occurred_at、idempotency_key。

### 3.4 wallet_ledger

`id`、wallet_id、entry_type（topup、authorization、release、usage_debit、refund、adjustment、commission_debit）、amount、currency、balance_after、source_type、source_id、idempotency_key、created_at。

### 3.5 commission_ledger

`id`、channel_org_id、beneficiary_role_id、source_usage_event_id、source_commission_id、policy_version、base_amount、rate、calculated_amount、final_amount、status、freeze_until、settlement_method、reversal_of、created_at。

### 3.6 quota_account / quota_allocation / quota_ledger

- `quota_account`：记录 A 用户余额、B/C 渠道可用额度或 B/C 用户服务额度的当前汇总。
- `quota_allocation`：记录 B/C 代理商根据下属用户充值向其发放服务额度的关系、额度上限、已用额度、有效期和状态。
- `quota_ledger`：记录 reseller_topup、platform_grant、end_user_topup、quota_issue、quota_reclaim、usage_debit、manual_adjustment、expiry 等不可变流水。

B/C 用户请求前校验其 allocation 可用额度，同时校验渠道剩余额度；请求结算时只产生一笔 `usage_debit`，并在同一事务中减少用户 allocation 和渠道可分配额度。

## 4. 请求扣款状态机

```text
余额校验
  -> authorization（预授权）
  -> upstream attempt(s)
  -> usage received
  -> charge committed + authorization released
  -> commission frozen
```

异常路径：

- 上游未响应：预授权过期释放；如果已产生可计费成本，进入待对账。
- 上游失败且 fallback 成功：客户只结算最终业务请求的约定费用；每次 attempt 成本单独记账。
- 客户中断流式响应：按上游实际 usage 和产品规则结算，不用 HTTP 连接是否完整作为唯一依据。
- usage 缺失：按提供商适配器规则处理并标记 `usage_pending_reconciliation`。

媒体 usage 除 token 外还应支持 `video_seconds`、`resolution_tier`、`fps`、`image_count`、`audio_seconds`、`request_units` 等计费维度。Seedance 等模型可能返回 token usage 与时长/分辨率并存，最终金额必须由 price rule 根据实际返回值计算。

## 5. 价格与毛利

至少维护三种价格：

- upstream_cost：平台向提供商承担的成本。
- channel_wholesale_price：给 B/C 计算额度和佣金基数的批发价。
- customer_sell_price：终端用户实际扣款价格。

可选第四种：channel_customer_price，用于 B/C 自定义终端售价。历史请求必须保存四种价格的快照及 price_version。

报表至少计算：收入、上游成本、渠道批发成本、佣金负债、支付手续费、退款损失、毛利和毛利率。

## 6. 一致性与并发

- 余额预授权使用数据库行锁或等价原子条件更新：`available_balance >= reserve_amount`。
- 结算和流水写入同一事务；异步指标和报表通过 outbox 事件更新。
- usage_event、charge、commission_ledger 均需唯一幂等键。
- 结算任务可重复执行；发现已处理的幂等键时返回原结果。
- 对账任务按 request_id、provider_request_id、wallet ledger 和支付 webhook 做日终差异报告。

支付采用适配器接口：`create_order`、`query_order`、`verify_callback`、`refund`、`normalize_event`。业务层不依赖具体支付品牌，只处理统一的 payment_order/payment_event 状态。每个适配器可声明支持的币种、支付方式、退款能力和回调格式；支付事件必须验签、幂等并保留原始报文引用。

订阅采用 `product_plan`、`subscription`、`entitlement` 和 `entitlement_ledger` 建模。权益账本记录 plan_grant、bonus_grant、renewal_grant、usage_debit、expiry、reversal；套餐权益与现金钱包分开，自动续费只改变订阅和权益状态，不直接修改历史消费流水。

## 7. 安全边界

- 凭据使用 KMS/应用层信封加密；数据库仅保存密文和指纹。
- 管理员敏感操作启用 2FA/二次确认；审计日志 append-only。
- 上游 Base URL 使用 allowlist；生产禁用任意私网地址和不安全 HTTP。
- 客户 API Key 支持长期查看；数据库保存加密密文和 hash 索引，查看、复制、轮换、禁用和过期均写审计日志，支持前缀和二次验证。
- 日志默认不保存 prompt/completion；需要保留时按租户策略脱敏和自动删除。
- 代理 IP 只信任明确配置的反向代理来源，避免 forwarded header 被伪造。

## 9. 迭代顺序

1. 先完成实体、账本、usage 事件和 API Key；用测试验证并发扣款、幂等和冲正。
2. 再接入一个 OpenAI-compatible 提供商，完成模型映射、健康检查和 fallback。
3. 再加入媒体异步任务、Seedance 适配器、资产存储和媒体计费。
4. 再加入多提供商路由、报表和支付 webhook。
5. 最后把分销佣金挂到已稳定的 usage 结算事件上，避免分销逻辑反向侵入网关扣款。
